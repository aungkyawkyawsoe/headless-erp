## ALWAYS APPLY — Engineering & Analysis Principles (every task, question, design, or code change)

Apply these lenses before answering or writing code. When a decision trades one against another, name the trade-off explicitly.

**Complexity & behaviour**

- **Asymptotics / Big O** — state the complexity of any algorithm, query, or loop you introduce; spot the dominant cost (N+1 queries, unbounded scans, per-row awaits). Prefer the bounded/Paginated/constant-per-call shape.
- **Granularity** — split responsibilities at the right seam: one reason to change per unit; avoid god classes AND premature abstractions.
- **Determinism** — same input ⇒ same output; pin ordering (explicit `ORDER BY`, no accidental `db.first` on a set), stable iteration, no reliance on row order, locale, or wall-clock except where the domain demands it.
- **Statelessness** — Workers isolates are ephemeral and reused: never depend on in-isolate state surviving a request; any cross-request state goes to D1/KV/R2/DO, and cached state must carry an invalidation key (see authz-version stamp).
- **Idempotency** — every write path must tolerate replay: upserts over blind inserts, deterministic keys, idempotency keys on writes, migrations re-runnable safely.

**Truth & communication**

- **Single Source of Truth / Single Version of the Truth** — one canonical place per fact (schema, config, registry, contract). Deriving the same fact twice in different code is a bug waiting to happen — collapse to one source and derive the rest.
- **Data Lineage** — know and be able to say where a number came from (which table/derivation); a report or denormalized field must trace back, and derived values must state what invalidates them.
- **Systems Thinking** — reason about the whole loop (producers, consumers, caches, retries, failure modes), not the local change; a fix must name where it propagates and what it can break.
- **Information Visibility** — make states/errors/degradation visible: a silent failure is the worst outcome; surface status, empty states, and failure reasons to the right consumer.
- **Minto Pyramid** — lead with the conclusion, then supporting arguments, then detail. Structure answers top-down, not chronologically.

**Structure & design**

- **MECE** — categorize/branch mutually exclusively, collectively exhaustively; no overlapping cases, no gaps. Enumerate the full case space before coding a conditional.
- **Data-Ink Ratio** (interfaces & docs) — every element must earn its place; cut decoration from UI copy, docs, and logs; ink = information.
- **Preattentive Processing** (UI) — make the important differences pop pre-attentively (colour/shape/position — e.g. status pill, destructive tint) so scanning takes milliseconds, not reading.

**Security**

- **PoLP (Least Privilege)** — grant the minimum capability; new surfaces start read-only or ungranted until a role needs them.
- **Poka-Yoke** — mistake-proof by construction: make wrong states unrepresentable (type constraints, schema validation, enum options, deny-by-default) instead of detectable after the fact.
- **STRIDE / PAST-STRIDE** — walk the threat model on any new surface: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege (and its PASTA-style counterpart analysis). Every gate, endpoint, and write path gets an owner and an answer for at least: who can call it, what it trusts, what it logs.

## 🚨 CRITICAL CONSTRAINTS (workerd runtime)

These are hard platform limits — do not reintroduce these patterns:

1. **`new Function()` / `eval` are DISALLOWED on the Workers runtime** (verified: "Code generation from strings disallowed"). Never use them in runtime code.
   - Expressions (linkage `calculate`, defaults, validation) use the **safe expression evaluator** in `packages/core/src/entity/expression.ts` — extend THAT if you need new syntax, don't reach for `eval`.
   - Server hooks and collection actions are **declarative (JSON rules)** — see the docs above. The legacy `function_code` (JavaScript) model was removed; the API rejects it.
   - ⚠️ The **Studio** runs in the browser (a dev tool) — Babel/live-compile is allowed THERE, never in `apps/api` worker code.
2. **`db.exec()` splits statements by newlines** — DDL must be single-line.
3. **`SELECT *` does NOT include SQLite's implicit `rowid`** — select `rowid` explicitly when needed (FTS5 `content=` tables map matches via `content_rowid`).
4. **D1 `MATCH ?1` binding fails in FTS5** — inline the search term as an escaped literal (`search.service.ts` does this).

## API Surface Summary (verified)

- All routes under `/api/*` require `Authorization: Bearer <token>` (dev: `dev-token` when `IS_DEV=true` — `IS_DEV` is **local-only**, set it in `apps/api/.dev.vars`, never in production `vars`)
- Rate-limit tiers (anonymous/auth/admin) are resolved from the bearer token by the limiter itself (see `resolveRateLimitTier` in `middleware/rate-limiter.ts`), so they work even before `requireAuth` runs
- Default admin login (dev): `dev@mmbics.com` / `dev-password-for-local-only` — from `ADMIN_USERNAME`/`ADMIN_PASSWORD`/`ADMIN_NAME` env (`headless init` writes **your** email/name/password to `apps/api/.dev.vars`)
- Auth providers (Clerk/Auth0/Supabase/OIDC) are wired into `requireAuth` — verify via `autoVerifyToken`
- **Authz decisions are version-keyed, not TTL-fresh** — every cached authz lookup (`PermissionEvaluator.checkBusiness` / `getFieldRestrictions` / `getRowFilter` and `AuthService`'s `user:` / `role:` lookups) appends `authz-version.ts`'s stamp — `MAX(updated_at)` across `_users` / `_roles` / `_role_permissions` — to its `CacheLayer` key. The `CacheLayer` is per-isolate and Workers reuse many isolates, so without the stamp a role/permission change served by ONE isolate kept serving the OLD answer from every OTHER for the whole TTL (the "changed the role but the mini app still shows the old access" report). A write anywhere bumps the data; the stamp itself is cached only ~1s, so the next read misses the stale entry with no cross-isolate invalidation channel, and every authz write path also calls `invalidateAuthzVersion()` for immediate local effect. `login`'s `last_login` touch is raw SQL on purpose, so a sign-in does NOT churn the stamp (and evict every authz cache). The mini-app also re-reads `/auth/me` on resume (`shared/auth.ts` `refreshMe()`), since the page-load `meCache` never re-fetched on in-app navigation. Pinned by `apps/api/test/authz-freshness.spec.ts` (raw D1 writes → next gated read reflects it) + `auth-profile-freshness.spec.ts`; see `docs/backend-api/authentication.md`.
- **A web (password) login signs in AS an employee, and offboarding revokes it** — `_users.employee_id` (migration `035_users_employee_id`, nullable + indexed) is the ONE link from a login identity to the person it acts as: a Telegram account needs none (its `tg-<id>@telegram.local` email IS the link — `findDirectoryEmployee` matches `hrm_employees.etg_id`), so exactly one of the three identity sources applies per row (Telegram email XOR employee link XOR neither = the bootstrap admin). `AuthService.login` mints the token WITH that employee (`generateToken(user.id, secret, user.employee_id)`), because every server-scoped action (punch, leave, custody, transfers) resolves its actor from the signed token — without it a web session could read but not act, which is exactly what it did before. `_healActingEmployee` is now KIND-aware and re-validates on EVERY request: a Telegram session still HEALS through the tg id (a re-pointed directory re-binds instead of logging out), a password session resolves through the account's own link and returns `null` — refusing the bearer outright — when that employee is gone, so terminating someone ends their web session the way the `etg_id` gate always ended their Telegram one. An account with NO link keeps its token's employee id untouched (a machine key / row-scope probe embeds a scope marker the directory does not own — re-resolving those would break their contract). The sign-in refusal is deliberately TWO messages: generic `Invalid email or password` before the password verifies (`status !== 'active'`, no enumeration) and an actionable `not linked to an active employee` AFTER it, where only the account's own owner can arrive. `employee_id` is the one UPDATE field applied on `!== undefined` rather than truthiness, so it can be UN-SET (`null` = unlink, `undefined` = leave alone) and a link is refused at write time unless it names a live employee. The Studio Users table shows the link for EVERY kind (a Telegram row resolves through its address) and degrades harmlessly where `hrm_employees` does not exist. Pinned by `apps/api/test/web-login-employee.spec.ts` (incl. a negative control: dropping the revoke branch fails the 401 assertions) + `apps/studio/src/lib/users.spec.ts` + `users-tab.spec.tsx`; see `docs/backend-api/users-roles-permissions.md` §_The employee link_.
- Field encryption initializes once per isolate in the config middleware (`index.ts`)
- Smart entity pipeline: `SmartCollectionService` wraps `CollectionService` adding linkage + defaults + validation; entity routes use it
- **Write responses carry a change envelope** — `meta.changed = { collections, rows }` names every collection a write touched (its own row + cascade parents + hook/denorm writes), captured request-scoped via `AsyncLocalStorage` (`apps/api/src/lib/change-scope.ts`) from the existing `invalidateCollectionReads()` seam and attached automatically by `success()`. Reads carry no such key. Clients invalidate precisely via `@mmbix/sdk`'s `onChange` (tgapp wires it in `shared/api/sdk.ts`); the `packages/sdk/test/client.test.ts` + `apps/api/test/change-envelope.spec.ts` pin it.
- **Reads are conditional (`ETag` / `304`)** — `success()` stamps a weak `ETag` (a hash of the exact bytes) on every 200 GET and answers a matching `If-None-Match` with a bodiless `304`. No version is stored and nothing is invalidated: the tag IS the content (a write changes the bytes → changes the tag), RBAC makes it per-user safe, and it holds across isolates. Only reads are conditional; version-based tags on the app manifest / MVE routes are preserved. `@mmbix/sdk` revalidates automatically (memory-only body store, `conditionalGet: false` to opt out) — pinned by `apps/api/test/conditional-get.spec.ts` + `packages/sdk/test/conditional-get.test.ts`. See `docs/backend-api/entities.md`.
- **Offline reads are opt-in per collection, advertised per response** — a successful read of a collection whose `schema_json.policies.offline_reads.enabled` is true carries `X-Offline-Max-Age: <max_age_s>` (absent ⇒ clients MUST NOT persist the body). Deny-by-default because persisting rows moves them to a device where logout/erasure cannot reach them — unlike `cache`, which stays in server memory. The policy is set in the Studio policy panel (`PolicyPanel.tsx`, reachable from the **Collections workbench** toolbar — where schemas are curated — and the **App workbench** toolbar) via `PUT /api/collections/:slug/policies`, read by `advertiseOfflineRead()` on the list + detail routes (`routes/entities.ts`), and obeyed by `@mmbix/sdk` (`ConditionalResponseCache` + `localStorageResponseStorage`, fingerprint-scoped, logout clears it, a 304 slides the window). A header rather than a `meta` key so it covers list and detail uniformly and a policy flip lands on the very next read. Pinned by `apps/api/test/offline-reads.spec.ts` + `packages/sdk/test/offline-reads.test.ts` + `packages/core/src/policy/__tests__/policy-resolver.test.ts`; the Studio half by `apps/studio/src/lib/policy-form.spec.ts` (raw↔form mapping, clamping) + `apps/studio/src/components/PolicyPanel.spec.tsx` (jsdom: switches toggle, Save PUTs, encrypted warning).
- **Writes are lockable per collection; identity is engine-bound** — a collection may declare, in `schema_json.policies` (set at create or via `PUT /api/collections/:slug/policies`; admin-only), `writes: { mode: 'service' | 'any', append_only, frozen_fields: string[], freeze_when: { field, values[] } }` and `actor_fields: string[]`. Enforced in `ItemMutationService.assertGenericWrite` / `stripFrozenFields` / `assertNotFrozen` / `bindActorFields` on the already-cached schema (zero extra D1 reads) and **inside** the service, so the RBAC admin bypass cannot reach a service-only table. `mode: 'service'` ⇒ the generic entity API is 403 (only the domain service writes); `append_only` ⇒ update/delete/restore rejected; `frozen_fields` ⇒ workflow columns silently stripped from a generic write (only the service sets them); `freeze_when` ⇒ once `row[field]` is one of `values` the row is POSTED and update/delete/restore are 403 (a state-conditional freeze — what makes the MRO confirm headers immutable); `actor_fields` ⇒ stamped from the signed session on create and un-reassignable by a non-admin (the JWT carries `employee_id` — see `docs/backend-api/authentication.md`). This is what makes the MRO stock/ledger tables single-writer and the two-person rule un-forgeable. Pinned by `apps/api/test/mro-inventory.spec.ts` + `packages/core/src/policy/__tests__/policy-resolver.test.ts`; see `docs/backend-api/policies-operations.md`.
- **A posted MRO document is undone by ONE cancel verb whose behaviour the DOCUMENT decides, never a caller flag** — `POST /api/mro/{inbounds|outbounds|transfers|adjustments}/:id/cancel` replaces the old one-way `/inbounds/:id/reverse` (dead code: no client, no test, no doc). A `draft` is a pure lifecycle flip (no stock ever moved), a `confirmed` document is **REVERSED in the same atomic guarded batch that flips it** (header flip LAST; any lost guard rolls the whole batch back with the reason), and an already-cancelled one is an idempotent no-op returning `already: true` + the ORIGINAL `cancelled_at`/`cancelled_by`. There is no mode parameter on purpose: a client that had to choose between "cancel a draft" and "reverse a posting" could choose wrong, and a wrong pick writes a conflict into the stock ledger — so `cancelled` cannot mean two things to two screens. A reversal reads the confirm's OWN TRACE (`mro_outbound_lots`/`serials`, `mro_adjustment_lots`/`serials`, `mro_transfer_lots`/`serials` — written by the confirm batch), never a re-derived FEFO/serial pick (which would hit DIFFERENT lots/units), and REFUSES (409, nothing applied) rather than guess: partly consumed stock, a lot drawn on, a unit that has since been seated/returned/moved, a receipt with money a PERSON recorded, a serial `return` (its prior holder is not recorded), a transfer whose destination has drawn on the moved stock or whose unit has left the destination since (its own trace then does not account for the line exactly). Money is provenance-marked both ways — the confirm's own `paid_at_receipt` ledger entry carries `_meta = {"source":"paid_at_receipt"}` so the un-post withdraws exactly that one, and a compiled `before_insert` guard refuses any payment whose parent receipt is `cancelled` (a void document takes no money, on every writer). The four headers also declare `freeze_when doc_status: ['confirmed','cancelled']` + `frozen_fields: ['cancelled_at','cancelled_by']`, so the engine's generic `cancelled → draft` reopen is refused (a reversed posting can never be re-applied under the same number) and the stamp can be neither forged nor cleared — the correction path is a NEW document. The mini app mounts ONE shared hook for all four families (`apps/tgapp/src/shared/hooks/use-doc-cancel.ts`, with `cancelCopyOf` deriving the one "nothing was moved" vs "the stock goes back" wording) on every list card AND document page (the inbound/outbound/adjustment screens and the stock-move card + detail page), and the affordance is ONE shared ⋮ actions menu (`apps/tgapp/src/shared/components/doc-actions-menu.tsx`) rather than a second labelled button: a draft keeps its explicit Confirm/Approve on the row (that IS a draft's job) while the cancel — a destructive, final reversal — sits one deliberate gesture away in the menu, on both surfaces, rendering `cancelCopy.label` as its entry so the entry the operator pressed and the sheet's own confirm button read the same string. A `cancelled` document renders read-only with NO menu at all (the component returns `null` when nothing is behind it), and `DocumentSummaryCard`/`ErpRow` carry a `trailing`/`menu` top-right slot for it. Pinned by `apps/api/test/mro-inventory.spec.ts` (`document cancellation — ONE verb, the DOCUMENT decides`, incl. the four transfer cases) + `apps/api/test/guarded-batch.spec.ts` (the WHOLE op vocabulary — each op's rollback is the exact opposite of its statement, both directions) + `apps/tgapp/src/shared/hooks/use-doc-cancel.spec.ts` + `apps/tgapp/src/modules/inbounds/{components/inbound-purchase-card,components/inbound-doc-card,pages/inbound-detail-page}.spec.tsx` + `apps/tgapp/src/modules/stock-moves/components/stock-move-card.spec.tsx`; see `docs/backend-api/mro-inventory.md` §5b/§5c.
  - **The menu entry is wired to `onClick`, never `onSelect`** — base-ui's `Menu.Item` renders a `<div role="menuitem">` and its props carry `onClick` only; an `onSelect` prop type-checks (React's DOM `onSelect` is the text-selection event) and then silently does nothing, which is exactly how the purchase card's Record-payment / Confirm / cancel entries were dead. Every other consumer in the repo already used `onClick`; pinned by `inbound-purchase-card.spec.tsx` (`actually RUNS the entry it was given`) + `stock-move-card.spec.tsx` (the cancel sheet opens off a menu click).
  - **A stock-document ROW's top-right corner is the LIFECYCLE, not the money** — all four stock cards deliberately leave `ErpRow`'s `trailing` (the bold header value) UNSET: the corner carries the status pill, the disclosure chevron and then the ⋮ (the menu LAST, rightmost, where a thumb reaches), so one scan of the list answers "draft or posted? and what can still be done?" — and the total/qty is not read twice (it rides the disclosure facts, or the leading tile for a qty). The chevron drops its `-mr-1` bleed when a ⋮ follows it, so two adjacent controls never share a tap target. Pinned by `apps/tgapp/src/modules/goods-issues/components/outbound-doc-card.spec.tsx` (status + ⋮ lead the corner, the total is one tap away).
- **A composite (`table`-field) write drops the CHILD collection's cached reads too** — `ChildTableService.createChildren` / `replaceChildren` land rows in the child collection's OWN table, so invalidating only the parent slug left a reader keyed on the child collection (the document page's own line read, `filter[parent_id][_eq]=…`) serving the PRE-SAVE lines until the response cache's TTL — a draft could be saved (its children replaced delete-and-recreate) and reopening it showed the old lines. Both writers now end by calling `invalidateCollectionReads(childSlug)`, which clears `readc:<child>:*` plus its `readdep:` tag AND, through the recorded observer, names the child in the write's `meta.changed.collections`, so clients drop it precisely too. Pinned by `apps/api/test/child-table-cache.spec.ts` (a raw-D1 mutation proves the cache entry is genuinely live, then a composite PUT _and_ CREATE must be reflected on the very next child read, and the envelope must name the child).
- **The response cache is dependency-tagged, not own-rows-gated** — a `?fields=`-expanded read IS cached: `ItemQueryService.readDependencies()` walks the selection and returns the set of collection slugs the payload embeds (recursively, depth ≤ 3; `null` ⇒ unbounded ⇒ never cached), stored on the entry as tags. A write to any embedded collection drops the entry even though the writer only knows its own slug (`invalidateCollectionReads` also calls `cache.invalidateTag('readdep:<slug>')`). This replaced a coarse "relation reads are never cached" gate. Pinned by `apps/api/test/relation-cache.spec.ts` + `packages/core/src/cache/__tests__/{cache-layer,response-cache}.test.ts`.
- **A purchase receipt's money state is DERIVED from a payment ledger** — `mro_inbound_payments` holds one row per payment (`paid_on`, `amount`, `method`, `reference`, `recorded_by` session-stamped); the header mirrors it as `paid_amount` / `payment_status` (`unpaid|partial|paid`) / `fully_paid_on` (the day the last instalment cleared the total). The mirror is re-derived from the LIVE ledger by compiled hooks in `apps/api/src/domain-modules/mro/inbound-payments.ts` (registered in `mountDomainModules`) after every payment write AND every header write — one guarded `UPDATE` that lands only when a value differs, so a re-run is a no-op. The rule itself is ONE pure function (`derivePaymentState`) fed by ONE aggregate query (LEFT JOIN … GROUP BY), so card, report and tests can never disagree. A recorded payment is **immutable**: `frozen_fields` could NOT express this (the engine strips frozen columns from the CREATE too, so the row could never be filed), so a compiled `before_update` guard refuses any change to amount / date / method / receipt — the correction path is soft-delete + re-file. The mini app files through `POST /api/mro/inbounds/:id/payments` (same engine create + an AWAITED derivation, so the response already carries the new figures) while Studio/CLI/import use the generic API and get the async hook. The mini app files AND removes through the receipt's own routes — `POST /api/mro/inbounds/:id/payments` and `DELETE /api/mro/inbounds/:id/payments/:paymentId` — both gated on `write` for `mro_inbounds`, because NO operational role carries `delete` on the ledger (the generic delete 403s an operator with `You do not have "delete" permission on "mro_inbound_payments"`); the DELETE route refuses a payment belonging to another receipt (409) and is a no-op on replay that still returns the receipt's current money state. A receipt can also arrive SETTLED: `mro_inbounds.paid_at_receipt` (the create form's `Paid in full` checkbox) is a draft-only flag whose CONFIRM files ONE ledger entry inside the same atomic batch (amount = the total the confirm computed, `paid_on` = the receipt date, recorder = the confirming session actor), refusing it for a kind that owes nobody or a receipt with no total — so “paid at receipt” can never exist without the money behind it. The CONTROL is draft-only too (`!readOnly && type === 'purchase'`): a settled receipt renders no `Paid in full` box and no sentence, because that copy describes what CONFIRMING will file (which already ran) and the money is on the ledger — a fully-paid receipt is stated by its money face, never by a dead checkbox. Pinned by `apps/api/test/mro-inventory.spec.ts` + `apps/tgapp/src/modules/inbounds/components/inbound-purchase-card.spec.tsx` + `inbound-detail-page.spec.tsx` + `inbound-doc-form.spec.tsx`. The mini app shows the money on ONE card used in two frames — the list row and the detail page that row opens onto (`variant="page"`: the store as a header fact, the document's LINE ITEMS attached under the money face inside that same card, no tap-to-open) — so the figure cannot read one way on the list and another on the page; an opening balance / return owes nobody and keeps the generic summary card. - **A stock document's detail page IS its form, and its STATUS decides edit vs read-only** — ALL FOUR MRO documents share this shape: `/app/inbounds/:id` mounts `InboundDocForm`, `/app/outbounds/:id` `OutboundDocForm`, `/app/adjustments/:id` `AdjustmentForm` and `/app/stock-moves/:id` `StockMoveForm` — the very components the `/+` create screens host, each seeded by ONE read (`fetchInboundDocEditor` / `fetchOutboundDocEditor` / `fetchAdjustmentDocEditor` / `fetchTransferDocEditor`: the header projection (`EDITOR_FIELDS`, or the list's own `HEADER_FIELDS`) + the child lines, mapped twice — `card` for the money/lifecycle face, `seed` for the fields) and mounted only after both resolve, because the form seeds its state once and a form that came up on the header alone would save the document empty; the form is `key`ed on the id so another document REMOUNTS it. A `draft` SAVES with `PUT` (the `lines` child table is REPLACED by the payload, so a removed line really leaves the draft and a re-send is idempotent); anything else renders the identical layout read-only, because `isInboundEditable` / `isOutboundEditable` / `isAdjustmentEditable` / `isTransferEditable(docStatus)` mirror the engine's own two rules (`writes.freeze_when doc_status:confirmed`/`cancelled` + the core draft→cancelled-only transition) rather than a caller flag — the screen never offers a write the server would 403. One derived `locked = submitting || readOnly` disables every control; ACTIONS (add/remove a line, the submit bar, every picker sheet) are ABSENT rather than dead. **A settled document never states the same fact TWICE — the pill IS the statement**: all four pages render the ONE shared `DocStatusPill` (`shared/components/doc-status-pill.tsx`, pinned by its own spec) off `MRO_DOC_STATUS_META`, and its optional `kind` rides INSIDE the badge (`Purchase · Confirmed`) for the ONE family whose form drops a kind control once the document is settled — editing an inbound's `type` IS a write (it decides the counterparty column the engine's `required_if` demands), so a settled receipt renders NO Type selector rather than three dead tabs and the pill carries the kind it is stuck on. Nothing then explains the read-only form: the `lockedReasonOf` sentence (first inside the form, then under the pill) was that same fact in a second voice and is DELETED, together with the `settled`/`reversal` vocabulary only it consumed — `cancelCopyOf` keeps one shared `DOC_NOUN` table of family nouns, and the footer carries only the draft's action. The four document pages are otherwise ONE layout, so a piped-in form and a settled one cannot drift: the form root's section gap and the line card's density (`gap-2` / `p-2.5` / `mt-1.5`) are the same on all four, the header's PAIR sits in ONE row wherever a form has one (`FIELD_ROW_CLASS`, `shared/components/form-styles.ts` — the receipt's counterparty beside its store, the issue's date beside its store; the sheets behind the pickers render no element of their own, so the row's cells are exactly the two fields, pinned by the two form specs), every date FIELD states the app's SHORT day-first format (`20 Sep 2026` — `APP_DATE_FORMAT` in `shared/time/myanmar.ts`, handed to the DS `DatePicker`'s `format` prop, which `formatDate` assembles part-by-part because a locale would order it month-first; the DS default stays the long `PPP` for the studio, and the ordered pattern is pinned by `packages/design-system/src/lib/date/format.test.ts`), and the Items heading now states only its label + the Add action: the running `Total quantity` PILL was REMOVED from the inbound and outbound forms (the row itself states the count it carries, so a second figure was ink without information — the adjustment/stock-move forms still carry theirs). An edit STATES the clearable fields where a create simply omits them, so a draft can change its shape without leaving a stale counterparty behind: inbound sends the counterparty PAIR (`supplier` XOR `handed_by`) plus `note: null` / `paid_at_receipt: false`; outbound sends the HOLDER pair (`to_vehicle` / `to_employee`, one id + one `null` — switching a draft from a truck to a person, or dropping its last serial line, must not leave the old holder set beside the new one) and `note: null`, and RE-STATES the source `request` so an edit can neither drop the link nor invent one. The two documents with no money face follow the same writable-field discipline: adjustments send `description: null` when it was emptied and stock-moves `note: null`, and BOTH omit `reported_by` entirely — it is an `actor_fields` column (the engine stamps it from the session on create and deletes it from a non-admin update, and the two-person rule `approved_by != reported_by` is built on it), so the form HIDES its `Reported by` section on an edit rather than claim the current user filed somebody else's report. Because the child table is REPLACED, any column the form does not itself collect is RE-STATED from the stored row rather than silently dropped: `mro_adjustment_lines.unit_cost` and `mro_outbound_lines.unit_price` (the latter drives the confirm's `total_amount`). A seeded row also keeps its OWN `mro_item_model` id as the payload key — the cached directory only NAMES the SKU — so a line whose SKU is missing from that read is saved AS IT WAS instead of vanishing from the document (all four forms take `modelOf(line)?.id ?? line.modelId`). Two batch rules that the confirm would otherwise enforce only after a save: an outbound line has NO batch field at all (`mro_outbound_lines` has no such column — allocation is FEFO by the engine's rule), while an adjustment's lot is an **`add`-only** field the confirm REQUIRES (`adding batch stock needs a batch_no`) — so the form blocks the save until it is typed, and `setDirection` CLEARS it when a row becomes a `remove` (whose lots the engine picks FEFO and records in `mro_adjustment_lots`). Two outbound-specific rules: the document's OWN `type` outranks the route's `?type=` (the tab an operator came from is navigation state, the column is the document), and a seeded row carries the STORED line's `modelName` / `tracking` as the fallback for while the cached SKU directory is still in flight (without it a serial row would briefly render as a plain consumable and its unit picker would vanish) — a re-picked model CLEARS both, since they described the SKU the operator just moved off. Money stays OUT of the inbound form — a separate tappable strip below it, since the ledger writes it, not the receipt. Pinned by the four `data/edit.spec.ts` (inbounds, goods-issues, adjustments, stock-moves) + `apps/tgapp/src/modules/{inbounds,goods-issues}/pages/{inbound,outbound}-detail-page.spec.tsx` + `apps/tgapp/src/modules/{adjustments,stock-moves}/pages/{adjustment,stock-move}-detail-page.spec.tsx` + `components/{inbound,outbound}-doc-form.spec.tsx`; the seed types are `InboundFormSeed`/`InboundLineSeed`, `OutboundFormSeed`/`OutboundLineSeed`, `AdjustmentFormSeed`/`AdjustmentLineSeed` and `TransferFormSeed`/`TransferLineSeed` in each module's `data/types.ts` (the stock-moves screen keeps the `mro_transfers` naming — `isTransferEditable` / `fetchTransferDocEditor`).
- **A serial line's units are entered in a SHEET, never a comma-separated text field** — `SerialEditorSheet` (one entry box + `Add` on top, one row per unit below, an `n/qty` counter in the header) is the only place a serial is typed, in create AND edit mode; the line's own field is a BUTTON that states the units (the comma list) and opens it. `addSerials` (`data/line-rules.ts`) is the one rule: `parseSerials` splits a whole pasted column in one Add, and a unit already on this line — or on ANOTHER line of the same receipt, which the form passes in — is REFUSED WITH ITS REASON rather than silently dropped, compared case-insensitively (`ty-1` = `TY-1`, which is one unit to the engine's uniqueness check). A serial names ONE physical unit, so a repeat either double-counts stock or makes the confirm 409 after all the typing. Deliberately NOT capped at the qty: blocking the serial side would trap an operator whose QUANTITY is the typo, so the sheet says which way the mismatch runs instead. On a SETTLED document the SAME sheet opens as a VIEWER (`readOnly`: no entry box, no `Add`, no per-row delete, no count instruction — an ACTION is absent rather than dead, and only an in-flight save holds the trigger back, `disabled={submitting}`), because the units a posted receipt received are a fact the operator must be able to read and the line's own field can only show them as a truncated comma list. **Every surface that names a SKU states the SAME pair — the parent item NAME over the SKU (`Tyre · 11R 22.5`)** — the picker row (`mroItemModelLabel`), the line card (`mroItemLineLabel`, whose fallback chain keeps a seeded SKU the cached directory does not know named, then its id, then `Select item`) and the serial sheet's title, so one SKU can never read two ways on two screens. Pinned by `apps/tgapp/src/modules/inbounds/components/serial-editor-sheet.spec.tsx` + `data/line-rules.spec.ts` + `components/inbound-doc-form.spec.tsx` (incl. the read-only view: the units list, with the entry box / `Add` / delete absent) + `shared/hooks/use-mro-item-models.spec.ts` (`mroItemLineLabel`).
- **The hook depth guard is scoped to the async chain, not the isolate** — `withDepthGuard` (`core/plugin-hooks.ts`) keeps its depth in an `AsyncLocalStorage`, because `after_*` hooks are dispatched FIRE-AND-FORGET: a shared module-level counter let a hook backlog from one request inflate the depth a LATER unrelated request observed, 500-ing a write that had no recursion at all ("Hook recursion cap reached"). A genuinely recursive chain still trips `MAX_HOOK_DEPTH`; two independent chains no longer share a budget.
- **Search mode is a per-collection policy (`contains` vs index-backed `prefix`)** — the generic `?search=` term matches via `schema_json.policies.search: { mode: 'contains' | 'prefix', fields: string[] }`, resolved by the same PolicyResolver that carries `cache`/`writes`. `contains` (`LIKE '%term%'`, the default, any collection) is correct everywhere but a leading wildcard cannot use an index; `prefix` (`LIKE 'term%'`) is the type-ahead shape ERP list screens use and an ordinary index on a declared `fields` entry serves it as a bounded range seek. Prefix applies only when ≥1 declared field is a real column, else the read falls back to contains (deny-by-default: an undeclared collection keeps today's behavior). The term is **escaped in both modes** (`LIKE ? ESCAPE '\'`), so a literal `%`/`_` matches its own bytes instead of every row — that was a silently-wrong result, not noise. Emitted in one place (`QueryParser.applyToQueryBuilder`, threaded from `ItemQueryService.listItems`/`runAggregate`); `mro_stock_serials` declares `prefix` over the indexed `serial_no` for the tgapp tyre type-ahead. Pinned by `apps/api/test/mro-inventory.spec.ts` + `packages/core/src/policy/__tests__/policy-resolver.test.ts`; see `docs/backend-api/policies-operations.md`.
  - **MRO asset custody = one rule with three direct shapes and four governed ones** — `assertCustodyChangeAllowed` (`domain-modules/mro/inventory/custody.ts`) asks ONE question of every writer: does this write change the unit's HOLDER? A **store → truck** (`/fit`), **store → employee** (`/issue`) and **same-truck seat change** (`/move` — a rotation keeps the holder) are DIRECT because the holder does not change. A **truck→truck**, **person→person**, **holder→store** or **holder→scrapped** change is the approval-gated shape: the raw `/move`, `/return` and `/scrap` routes answer **403** with server-owned copy (`… is changing holder — file a transfer request and have a superior approve it …`, `… is written off through an approved write-off request …`). A **truck↔person** move is refused on EVERY path — the only honest route is return-to-store then issue, and the tgapp filer offers exactly that. `mro_stock_serials` is `writes.mode: 'service'`, so the generic entity API cannot reach the table even as admin, and `authorizedBy` is passed by the service's own caller (never read from a body) — **an admin cannot bypass the gate**. Pinned by `apps/api/test/mro-inventory.spec.ts` + `apps/tgapp/src/modules/tyres/data/api.spec.ts` (`freeFitmentTargets` flags its OWN truck `sameVehicle`, which is the flag the DIRECT move's own-truck filter keys on — a cross-truck seat is a dead button, so it is never offered).
  - **Transfers, returns AND write-offs live in the SAME table (`mro_asset_requests`)** — the kind is DERIVED from the row's own shape rather than stored as a mode flag, so one table, one approver scope and one execute serve all three: `write_off` set (every destination null) is a WRITE-OFF, `to_location` set is a RETURN (holder → store), `to_vehicle`/`to_employee` is a TRANSFER. `executeAssetRequest` dispatches on that: `scrapMountedSerial({authorizedBy, expectFrom, refKind:'ATR', refDoc, compose})`, `returnSerialToStore(…)` or `moveSerialAsset(…)`. A compiled guard (`domain-modules/mro/asset-request-guard.ts`) refuses the ONE dangerous combination at create AND update — `write_off` carrying a destination (it would scrap a unit somebody believed they were moving) — while a destination-less row WITHOUT the flag stays a malformed transfer the move writer refuses, so a missing field never becomes a destructive default. The tgapp filer is destination-aware (`apps/tgapp/src/modules/tyres/data/transfer-targets.ts` — `custodyDestinationKinds`, pinned by its spec): a truck-held unit is offered another truck or the store, a person-held unit another person or the store, and NEVER across truck↔person; the write-off has its own page (`ScrapRequestSection`) because it names no destination, and the approval card names the kind it is (`requestKindOf`, so `Execute move` ≠ `Execute return` ≠ `Execute write-off`).
  - **MRO asset transfer = file → superior decide → atomic execute (`mro_asset_requests`, `ATR-…`)** — a truck→truck / person→person move, a store return OR a write-off is filed through the generic API (`requested_by` session-stamped; `status`/`approved_by`/`approved_at`/`rejected_reason`/`executed_at` frozen), decided by a recorded superior (`hrm_employee_links`; an admin may decide any) via `POST /api/mro/asset-requests/:id/approve|reject`, then executed by `POST /api/mro/asset-requests/:id/execute` — ONE guarded batch that performs the change the row's kind names (move / return / scrap) pinned to the request's recorded source (`expectFrom`) and flips `status='executed'`, appending the serial event tagged `ref_kind='ATR'` + `ref_doc=<display_number>`. Every decide route also needs an `actor_id` (the session's recorded employee) — a controller-less admin session gets `400 The deciding employee is required`, not a silent move. See `docs/backend-api/mro-inventory.md` §8c.
    - **The approver feed is the same scope as the decision** — `GET /api/mro/asset-requests[?status=&search=&cursor=]` returns the requests THIS session may decide (admin → all; else `requested_by ∈ my recorded subordinates`; no reporting line → empty feed, not an error), display-ready (serial / both plates / both custodians / requester / decider resolved server-side, plus `write_off` so a card can name the kind), `status` accepts a comma list (`approved,executed`), keyset-paged. The tgapp **Approval center** (`/app/approval`) is a thin 4-tab container — Early Leave / Leave / Overtime (`HrApprovals`) + **Transfers** (`AssetApprovals`, `apps/tgapp/src/modules/asset-transfers`, which carries moves, store returns AND write-offs) — and a holder files a request from the asset's serial page (`TransferRequestSection`) or, for a write-off, from the unit's action menu (`ScrapRequestSection`). The filer is `kind`-aware (the ONE `mro_asset_requests` table serves all of them): a **tyre** picks a destination **wheel position** (wheel-capable trucks only; its own truck stays, a rotation), an **asset** rides **loose on any plated truck** (its current truck excluded — the no-op the engine rejects) or goes to a person; that pure rule lives in `apps/tgapp/src/modules/tyres/data/transfer-targets.ts` (pinned by its spec).
  - **HR requests likewise read + decide through SERVER-scoped routes** — `GET /api/hr/requests[?type=leave|ot|early|all&scope=own|approve&status=&search=]` resolves the scope from the SIGNED session + `hrm_employee_links` (`own` = the session employee; `approve` = their recorded direct subordinates, or everyone for an admin; no reporting line ⇒ empty feed), and `POST /api/hr/requests/:kind/:id/decide` (`{ action: approved|rejected|cancelled, reason?, expectUpdatedAt? }`) enforces the same reporting line plus `can_approve` (an admin may decide any; only the requester or an admin may cancel). The client no longer supplies a filterable identity, and the Telegram role carries a **SELF-only row filter** on `hrm_leaves` / `hrm_overtimes` / `hrm_early_leaves` so the generic `/api/entities` read can never surface a colleague's `reason`. A punch's **TIME is server-owned**: `POST /api/hr/attendances/punch` stamps it, and the compiled `attendance-time-lock` hook re-stamps `check_in`/`check_out` on every write path (a trusted-root admin is exempt, keeping a deliberate back-fill possible). Pinned by `apps/api/test/hr-request-scope.spec.ts`; see it + the `hr` module under `apps/api/src/domain-modules/`.

- **A hard guard can be softened by ONE explicit, request-scoped acknowledgement** — a compiled guard sometimes refuses a write the caller may legitimately want anyway (the MRO same-day duplicate requisition is a WARNING: a split delivery occasionally has to be filed twice). Such a guard stays deny-by-default — every unconfirmed path (Studio, CLI, import, a blind retry) is still refused — and a caller that has SEEN the warning confirms it by naming the guard's token in the `X-Write-Ack` request header (`apps/api/src/lib/write-ack.ts`: an `AsyncLocalStorage` scope filled by ONE global middleware from that header, mirroring change-scope; the SDK sends it through `MutateOptions.ack`). The confirmation is REQUEST metadata, never record data, so it can never reach a row (a body flag would land in `_meta`). The verdict and the confirmation are the SAME rule: `POST /api/mro/requisitions/check-duplicate` runs the guard's own `findDuplicateRequisition` and returns `{ duplicate, message, display_number, ack }`, so the mini-app renders server-owned copy in its confirm sheet and never hardcodes a token. Pinned by `apps/api/test/mro-inventory.spec.ts` + `apps/api/test/write-ack.spec.ts` + `packages/sdk/test/items.test.ts`; see `docs/backend-api/mro-inventory.md` §8.
- **MRO stock reconciliation is one read-only, admin-gated integrity report (`GET /api/mro/stock/reconcile`)** — three bounded checks (no full-history scan): `balance_drift` (a balance row ≠ its derived lot/serial total), `orphan_stock` (lot/serial stock with no balance row), `snapshot_stale` (a serial's newest event postdates its snapshot row, at second granularity). Pinned by `apps/api/test/mro-inventory.spec.ts`; see `docs/backend-api/mro-inventory.md` §5.

## 🧱 Structure & conventions (do not regress)

### Studio = the visual app builder (`apps/studio`)

- **Schema designer (App workbench — `AppDetailPage.tsx`)**: create collections (New Model dialog → `POST /api/collections`), add fields from the 40-type catalog (`FieldTypesPanel.tsx`), type-aware field dialog (`AddFieldDialog.tsx`), field inspector (`FieldInspector.tsx` incl. linkage `visible_when`/`readonly_when`/`required_when` via `ConditionBuilder`), form-layout editor (`formlayout/`), permissions panel. All schema changes go through the same validated API as the CLI (DDL + cache invalidation handled server-side).
- **Menu builder + table/card view editors** (`MenuBuilder`, `TableLayoutCanvas`, `CardLayoutCanvas`) — per-menu view layouts stored in `schema_json`.
- **Runtime Policies panel (`PolicyPanel.tsx`)** — per-collection `auto_index` / `cache` / `offline_reads` toggles (the headless control plane, saved via `PUT /api/collections/:slug/policies`; no redeploy). Deliberately reachable from **two** toolbars with the SAME component: the **Collections workbench** (`CollectionsWorkbench.tsx` — where collections are curated) and the **App workbench** (`AppDetailPage.tsx`). Form state ↔ API mapping is pure and lives in `lib/policy-form.ts` (mirrors `DEFAULT_POLICY` in `packages/core`); the component only renders it.
- **Users table (`users-tab.tsx`)** — the `_users` registry, the Directus-style account table (name/email, how it signs in, role, status, last sign-in). Mounted with the SAME component from **two** surfaces, following the `RolesTab` precedent: **Studio Admin → Settings → Users** (`StudioAdminPage.tsx`) and the **IDP portal → Users** (`/idp/users`, `IdpUsersPage.tsx`) — roles and the accounts holding them are two halves of "who can do what?", so they cannot drift into two implementations. `_users` carries no `kind`/`provider` column and holds every principal in one table (bootstrap admin + password accounts + the Telegram-provisioned `tg-<id>@telegram.local` identities), so the kind is DERIVED in ONE place (`lib/users.ts` `identityKindOf`, a strict `/^tg-\d+@telegram.local$/`, never a bare suffix test) — and a Telegram row offers no password field and no writable name/role, because `findOrCreateUser` re-syncs those from the directory on every sign-in while the status switch DOES stick. `lib/users.ts` is also where `created_at` is read as UTC (SQLite `CURRENT_TIMESTAMP` has no `Z`, and `Date.parse` would shift every row by the operator's offset) and `userStateOf` answers `unknown` rather than claiming `active` for a status it was not given. An edit sends ONLY the changed fields (an identical re-send would touch `updated_at`, which every cached authz lookup keys off) and the operator can never disable their own account (that would revoke the session they are using; recovery is another admin). No credential is ever rendered — the API strips `password_hash` (`SAFE_USER_FIELDS`). `lib/users.ts` is ALSO where the employee column is resolved: for a password account through `_users.employee_id`, for a Telegram account through `telegramIdOf` + the directory's `etg_id` (so every account kind names the same employee the same way), with `Not linked` stated rather than left blank — and the ONE `TELEGRAM_EMAIL` pattern carries the capture group `telegramIdOf` reads, so the two can never drift into two patterns for one address shape. Pinned by `apps/studio/src/lib/users.spec.ts` + `apps/studio/src/components/admin/users-tab.spec.tsx`; the backend half (a disabled account is refused at login with the SAME 401 as a wrong password) by `apps/api/test/auth-disabled-login.spec.ts`, and the employee link by `apps/api/test/web-login-employee.spec.ts`.
- **Minecraft page canvas (`PageBuilder.tsx`)**: 12-column grid, Photoshop-style layer panel (`ComponentCatalog.tsx`), DB-driven keyboard shortcuts (`keyboard_shortcuts` in `studio.db`). There is no in-browser TSX compiler — widget/block code is written as real files in the design-system, never compiled in the worker runtime.
- **studio.db** (local SQLite, committed) drives the component catalog/meta — rebuilt via `node studio.db/build.js && node studio.db/seed-demos.js`; served by the vite plugin (`studio.db/vitePlugin.ts`, `/__studio/*` — dev-only, never `/api`). The `/__studio/meta` snapshot is fetched ONLY by the two screens that read it — the App workbench (`/apps/:slug`) and Studio Admin (`/studio`) — because `StudioMetaProvider` mounts per-route, so the login screen, apps gallery and IDP portal issue ZERO meta reads. Its wire is columnar (`src/lib/meta-codec.ts` — ONE codec shared by dev plugin + worker + client, ~39% smaller, lossless) and the worker edge-caches it under a `studio_config.meta_version` key bumped on every admin write, so a repeat read costs one version query. Raw `/__studio/prompt` stays unencoded (LLM-readable).

### Widgets = real design-system files (NO database)

- One widget = one file: `packages/design-system/src/components/widgets/<name>.tsx` exporting the component + a `widgetMeta` (registry entry with props schema).
- `packages/design-system/scripts/widgets.mjs` auto-generates the registry `index.ts` (`WIDGET_REGISTRY`, `widgetDefOf`, `widgetDefaults`); ui-views re-exports them.
- Editing widget code = edit the file directly (`packages/design-system/src/components/widgets/<name>.tsx`), then regenerate + rebuild (next bullet). There is **no** `/__studio/save-widget` route — the studio dev server only serves `studio.db` metadata (`/__studio/*`), it never writes widget files.
- After adding/changing a widget file: `node scripts/widgets.mjs` then `pnpm --filter @mmbix/design-system build` (apps consume the built `dist`).

### Conventions

- **Collections can be created via the Studio schema designer OR `POST /api/entities` OR `headless collection create`** — all paths converge on the same service. There IS a UI schema builder (the earlier "no UI schema builder" rule is obsolete).
- **A field is required (NOT NULL) unless `required: false` is explicit** — callers that build field lists must send `required: false` for optional fields.
- **`unique` is soft-delete-aware** — enforced by ONE partial index (`uidx_<table>_<col>` … `WHERE deleted_at IS NULL`), the same rule the engine's uniqueness pre-check and every read use, so a soft-deleted record never squats its value. Emitted identically by `SchemaBuilder.createTable`, `EntityMigrator` (in-place + rebuild) and the schema sweep; the sweep also normalizes a legacy inline `UNIQUE` constraint (an undeletable auto-index) into that shape. A raw DB unique violation maps to **400** `VALIDATION_ERROR` via `constraintViolation` (`packages/core/src/db/repository.ts` — the single classifier the Repository and the error handler share), never a 502. Pinned by `apps/api/test/unique-soft-delete.spec.ts`.
- **Business modules are scaffolded, not added to the factory core** — `headless module create` (templates in `packages/cli/templates`). The ONLY shipped business modules are the opt-in reference verticals in `apps/api/src/domain-modules/` (`hr/`, `idp/`, `mro/`) — self-contained folders mounted via `mountDomainModules(app)` and gated by `DOMAIN_MODULES` (`infra/env.prod` ships `hr,idp,mro`); the factory core (`routes/`, `plugins/`, `lib/`, `services/`) never imports them. No `modules/` folder, no `module add` — new verticals = copy a `domain-modules/*` folder or scaffold via the CLI.
- **The IDP domain-module (`/api/idp`) is the Studio's operate + govern surface** — catalog/scorecard/usage/templates reads + admin-gated environments/deployments/ownership writes and a `draft → review → promoted → live` deployment workflow. Three invariants keep it sound: (1) its four `idp_*` collections are provisioned once per isolate by an `app.use('*')` middleware (`IdpService.ensureCollections`, promise-memoized) — never lazily on one route only, or the first writer hits a missing table; (2) every workflow transition mirrors `to_state` onto `idp_deployment.status` (catalog + scorecard read that column, so it must never drift from `_workflow_states`); (3) raw writes/DDL in `IdpService` must call `invalidateCollectionReads()` / `SchemaService.invalidateCache()` — the engine's own writes do, and skipping it serves stale rows. Promotion + generic transitions are `requireAdmin`; pinned by `apps/api/test/idp.spec.ts`.
- **Design-system changes require a DS build** — `pnpm --filter @mmbix/design-system build` (components, widgets, exports).
- **Error codes are a canonical contract, not literals** — the single source is `@mmbix/types/contract.ts` (`ERROR_CODES`, `STATUS_TO_ERROR_CODE`, `errorCodeForStatus`). Any new failure code MUST be added to the catalog, not hardcoded: `fail()`, the error handler, and `@mmbix/sdk` typed errors all read from it, `GET /api/meta` advertises `data.error_codes`, and `apps/api/test/contract.spec.ts` pins it. Never hand-write a second error-code map (that was the drift this removed).
- The schema cache (`packages/core` CacheLayer) must be invalidated after DDL changes (create/update/delete collection, seed reset clears it via `cache.clear()`).
- **Studio URL/history contract — one rule everywhere** (`apps/studio/src/lib/view-state.ts`): a route PATH is real navigation (`navigate()`/`<Link>`, push); a route's QUERY PARAMS are that screen's view state and must never create history entries. All Studio URL-backed state MUST go through the `useViewState()` hook (`update`/`commit` rewrite the current entry — replace, never push) so each screen owns exactly one history entry and the back arrow leaves it in one press. Explicit "← Back" buttons must call `popBack(navigate, fallback)` (pop the entry beneath when one exists — mirrors `apps/tgapp/src/shared/platform/history.ts`). NEVER call `useSearchParams().setSearchParams` directly.

## Testing

- `pnpm test` (turbo) — core + utils + api suites
- API tests: `apps/api/test/*.spec.ts` (vitest + cloudflare pool) — always `cd apps/api && npx tsc --noEmit` + vitest after changes
- Studio: `cd apps/studio && npx tsc --noEmit && npx vite build` (typecheck is clean today — no pre-existing-error allowlist needed). Unit tests: `pnpm --filter @mmbix/studio test` (`vitest.config.mts`) — default environment is **node** for pure logic; a component test opts into a DOM with a `// @vitest-environment jsdom` docblock on line 1 and `@testing-library/react` (assert with plain DOM properties, e.g. `aria-checked` / `(el as HTMLButtonElement).disabled` — jest-dom matchers are deliberately not installed).
- Live smoke: `npx wrangler dev` then curl against `localhost:8788` with `dev-token`; SDK-side against a running dev API via `packages/sdk/test/live-smoke.test.ts`
