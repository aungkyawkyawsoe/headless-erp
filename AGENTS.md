## ALWAYS APPLY — Engineering & Analysis Principles (every task, question, design, or code change)

Apply these lenses before answering or writing code. When a decision trades one against another, name the trade-off explicitly.

**Complexity & behaviour**

- **Asymptotics / Big O** — state the complexity of any algorithm, query, or loop you introduce; spot the dominant cost (N+1 queries, unbounded scans, per-row awaits). Prefer the bounded/Paginated/constant-per-call shape.
- **Granularity** — split responsibilities at the right seam: one reason to change per unit; avoid god classes AND premature abstractions.
- **Determinism** — same input ⇒ same output; pin ordering (explicit `ORDER BY`, no accidental `db.first` on a set), stable iteration, no reliance on row order, locale, or wall-clock except where the domain demands it.
- **Statelessness** — Workers isolates are ephemeral and reused: never depend on in-isolate state surviving a request; any cross-request state goes to D1/KV/R2/DO, and cached state must carry an invalidation key (see authz-version stamp).
- **Idempotency** — every write path must tolerate replay: upserts over blind inserts, deterministic keys, idempotency keys on writes, migrations re-runnable safely.

**Truth & communication**

- **Single Source of Truth / Single Version of the Truth** — one canonical place per fact (schema, config, registry, contract). Deriving the same fact twice in different code is a bug waiting to happen — collapse to one source and derive the rest.
- **Data Lineage** — know and be able to say where a number came from (which table/derivation); a report or denormalized field must trace back, and derived values must state what invalidates them.
- **Systems Thinking** — reason about the whole loop (producers, consumers, caches, retries, failure modes), not the local change; a fix must name where it propagates and what it can break.
- **Information Visibility** — make states/errors/degradation visible: a silent failure is the worst outcome; surface status, empty states, and failure reasons to the right consumer.
- **Minto Pyramid** — lead with the conclusion, then supporting arguments, then detail. Structure answers top-down, not chronologically.

**Structure & design**

- **MECE** — categorize/branch mutually exclusively, collectively exhaustively; no overlapping cases, no gaps. Enumerate the full case space before coding a conditional.
- **Data-Ink Ratio** (interfaces & docs) — every element must earn its place; cut decoration from UI copy, docs, and logs; ink = information.
- **Preattentive Processing** (UI) — make the important differences pop pre-attentively (colour/shape/position — e.g. status pill, destructive tint) so scanning takes milliseconds, not reading.

**Security**

- **PoLP (Least Privilege)** — grant the minimum capability; new surfaces start read-only or ungranted until a role needs them.
- **Poka-Yoke** — mistake-proof by construction: make wrong states unrepresentable (type constraints, schema validation, enum options, deny-by-default) instead of detectable after the fact.
- **STRIDE / PAST-STRIDE** — walk the threat model on any new surface: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege (and its PASTA-style counterpart analysis). Every gate, endpoint, and write path gets an owner and an answer for at least: who can call it, what it trusts, what it logs.

# Headless Entity Engine — Backend API + Studio (this repo)

This monorepo is a **headless entity engine / software factory on Cloudflare Workers** with a **visual studio** (schema designer + page builder). The **factory core is generic** — this repo ships ONE factory-level module, `idp` (the Internal Developer Platform admin surface) under `apps/api/src/domain-modules/`; `DOMAIN_MODULES` gates which modules ship (`none` = pure factory). New business logic is added as a module (a `ModuleManifest` + routes), not to the core (Strapi/Frappe-style):

- `apps/api` — the API worker (Hono + D1 + R2), the `idp` module, and 29 gated plugins (`PLUGINS`). **All backend API docs live here.**

- `packages/types` — shared TypeScript types incl. the `ModuleManifest` contract (the tRPC `AppRouter` type is defined in `@mmbix/api` — import it from there for end-to-end type safety)

## 🚨 CRITICAL CONSTRAINTS (workerd runtime)

These are hard platform limits — do not reintroduce these patterns:

1. **`new Function()` / `eval` are DISALLOWED on the Workers runtime** (verified: "Code generation from strings disallowed"). Never use them in runtime code.
   - Expressions (linkage `calculate`, defaults, validation) use the **safe expression evaluator** in `packages/core/src/entity/expression.ts` — extend THAT if you need new syntax, don't reach for `eval`.
   - Server hooks and collection actions are **declarative (JSON rules)** — see the docs above. The legacy `function_code` (JavaScript) model was removed; the API rejects it.
   - ⚠️ The **Studio** runs in the browser (a dev tool) — Babel/live-compile is allowed THERE, never in `apps/api` worker code.
2. **`db.exec()` splits statements by newlines** — DDL must be single-line.
3. **`SELECT *` does NOT include SQLite's implicit `rowid`** — select `rowid` explicitly when needed (FTS5 `content=` tables map matches via `content_rowid`).
4. **D1 `MATCH ?1` binding fails in FTS5** — inline the search term as an escaped literal (`search.service.ts` does this).

## API Surface Summary (verified)

- All routes under `/api/*` require `Authorization: Bearer <token>` (dev: `dev-token` when `IS_DEV=true` — `IS_DEV` is **local-only**, set it in `apps/api/.dev.vars`, never in production `vars`)
- Rate-limit tiers (anonymous/auth/admin) are resolved from the bearer token by the limiter itself (see `resolveRateLimitTier` in `middleware/rate-limiter.ts`), so they work even before `requireAuth` runs
- Default admin login (dev): `dev@mmbics.com` / `dev-password-for-local-only` — from `ADMIN_USERNAME`/`ADMIN_PASSWORD`/`ADMIN_NAME` env (`headless init` writes **your** email/name/password to `apps/api/.dev.vars`)
- Auth providers (Clerk/Auth0/Supabase/OIDC) are wired into `requireAuth` — verify via `autoVerifyToken`
- **Authz decisions are version-keyed, not TTL-fresh** — every cached authz lookup (`PermissionEvaluator.checkBusiness` / `getFieldRestrictions` / `getRowFilter` and `AuthService`'s `user:` / `role:` lookups) appends `authz-version.ts`'s stamp — `MAX(updated_at)` across `_users` / `_roles` / `_role_permissions` — to its `CacheLayer` key. The `CacheLayer` is per-isolate and Workers reuse many isolates, so without the stamp a role/permission change served by ONE isolate kept serving the OLD answer from every OTHER for the whole TTL (the "changed the role but the client still shows the old access" report). A write anywhere bumps the data; the stamp itself is cached only ~1s, so the next read misses the stale entry with no cross-isolate invalidation channel, and every authz write path also calls `invalidateAuthzVersion()` for immediate local effect. `login`'s `last_login` touch is raw SQL on purpose, so a sign-in does NOT churn the stamp (and evict every authz cache). A client should re-read `/auth/me` on resume, since the page-load `meCache` must not go stale on in-app navigation. Pinned by `apps/api/test/authz-freshness.spec.ts` (raw D1 writes → next gated read reflects it) + `auth-profile-freshness.spec.ts`; see `docs/backend-api/authentication.md`.
- **A web (password) login signs in AS an employee, and offboarding revokes it** — `_users.employee_id` (migration `035_users_employee_id`, nullable + indexed) is the ONE link from a login identity to the person it acts as: a Telegram account needs none (its `tg-<id>@telegram.local` email IS the link — `findDirectoryEmployee` matches the configured directory tg-id field), so exactly one of the three identity sources applies per row (Telegram email XOR employee link XOR neither = the bootstrap admin). `AuthService.login` mints the token WITH that employee (`generateToken(user.id, secret, user.employee_id)`), because every server-scoped action (punch, leave, custody, transfers) resolves its actor from the signed token — without it a web session could read but not act, which is exactly what it did before. `_healActingEmployee` is now KIND-aware and re-validates on EVERY request: a Telegram session still HEALS through the tg id (a re-pointed directory re-binds instead of logging out), a password session resolves through the account's own link and returns `null` — refusing the bearer outright — when that employee is gone, so terminating someone ends their web session the way the tg-id gate always ended their Telegram one. An account with NO link keeps its token's employee id untouched (a machine key / row-scope probe embeds a scope marker the directory does not own — re-resolving those would break their contract). The sign-in refusal is deliberately TWO messages: generic `Invalid email or password` before the password verifies (`status !== 'active'`, no enumeration) and an actionable `not linked to an active employee` AFTER it, where only the account's own owner can arrive. `employee_id` is the one UPDATE field applied on `!== undefined` rather than truthiness, so it can be UN-SET (`null` = unlink, `undefined` = leave alone) and a link is refused at write time unless it names a live employee. The Studio Users table shows the link for EVERY kind (a Telegram row resolves through its address) and degrades harmlessly where the directory is not configured. Pinned by `apps/api/test/web-login-employee.spec.ts` (incl. a negative control: dropping the revoke branch fails the 401 assertions) + `apps/studio/src/lib/users.spec.ts` + `users-tab.spec.tsx`; see `docs/backend-api/users-roles-permissions.md` §_The employee link_.
- **Sessions outlive the JWT with a hash-only, single-use rotating refresh token** — `POST /api/auth/login` also mints a 256-bit refresh token (`_refresh_tokens`, migration `048_refresh_tokens`; SHA-256 hash at rest like `_api_keys`) and `POST /api/auth/refresh` rotates it single-use (successor via `rotated_from`, `device_id` bound at login and carried across rotations, 30-day sliding TTL). A refresh re-runs the full login gate (account `status: 'active'` + employee link live) — a refusal revokes the whole chain, so offboarding ends the bearer AND the refresh chain, not just the JWT window. Replaying an already-rotated token is a theft signal: the whole descendant chain dies and `securityAudit` records `reason: 'refresh_token_reuse'`; every failure answers the same generic 401 (no oracle). `POST /api/auth/logout` revokes the presented chain (`all: true` → every live chain of the user), idempotent and oracle-free (`{ revoked: N }`). Clients carry it end-to-end: `@mmbix/sdk` stores the chain beside the JWT (opt-in `TokenStorage.getRefresh`/`setRefresh`), rotates an expired token up front and on a 401 — SINGLE-FLIGHT, because racing rotations would trip the theft detector — and `auth.logout({ all? })` clears locally first, then revokes best-effort (`auth.refresh()` is the explicit rotation); `mex_flutter_sdk` (`packages/mex-flutter-sdk`, the single merged Dart/Flutter SDK) mirrors this 1:1 and `FlutterSecureTokenStorage` persists the second slot. Pinned by `apps/api/test/refresh-token.spec.ts`, `packages/sdk/test/client.test.ts` (`refresh tokens & logout`), `packages/mex-flutter-sdk/test/client_test.dart` + `packages/mex-flutter-sdk/test/secure_token_storage_test.dart`; see `docs/backend-api/authentication.md` §_Refresh Tokens & Logout_.
- Field encryption initializes once per isolate in the config middleware (`index.ts`)
- Smart entity pipeline: `SmartCollectionService` wraps `CollectionService` adding linkage + defaults + validation; entity routes use it
- **Write responses carry a change envelope** — `meta.changed = { collections, rows }` names every collection a write touched (its own row + cascade parents + hook/denorm writes), captured request-scoped via `AsyncLocalStorage` (`apps/api/src/lib/change-scope.ts`) from the existing `invalidateCollectionReads()` seam and attached automatically by `success()`. Reads carry no such key. Clients invalidate precisely via `@mmbix/sdk`'s `onChange` (a client wires it in its SDK setup); the `packages/sdk/test/client.test.ts` + `apps/api/test/change-envelope.spec.ts` pin it.
- **Reads are conditional (`ETag` / `304`)** — `success()` stamps a weak `ETag` (a hash of the exact bytes) on every 200 GET and answers a matching `If-None-Match` with a bodiless `304`. No version is stored and nothing is invalidated: the tag IS the content (a write changes the bytes → changes the tag), RBAC makes it per-user safe, and it holds across isolates. Only reads are conditional; version-based tags on the app manifest / MVE routes are preserved. `@mmbix/sdk` revalidates automatically (memory-only body store, `conditionalGet: false` to opt out) — pinned by `apps/api/test/conditional-get.spec.ts` + `packages/sdk/test/conditional-get.test.ts`. See `docs/backend-api/entities.md`.
- **Offline reads are opt-in per collection, advertised per response** — a successful read of a collection whose `schema_json.policies.offline_reads.enabled` is true carries `X-Offline-Max-Age: <max_age_s>` (absent ⇒ clients MUST NOT persist the body). Deny-by-default because persisting rows moves them to a device where logout/erasure cannot reach them — unlike `cache`, which stays in server memory. The policy is set in the Studio policy panel (`PolicyPanel.tsx`, reachable from the **Collections workbench** toolbar — where schemas are curated — and the **App workbench** toolbar) via `PUT /api/collections/:slug/policies`, read by `advertiseOfflineRead()` on the list + detail routes (`routes/entities.ts`), and obeyed by `@mmbix/sdk` (`ConditionalResponseCache` + `localStorageResponseStorage`, fingerprint-scoped, logout clears it, a 304 slides the window). A header rather than a `meta` key so it covers list and detail uniformly and a policy flip lands on the very next read. Pinned by `apps/api/test/offline-reads.spec.ts` + `packages/sdk/test/offline-reads.test.ts` + `packages/core/src/policy/__tests__/policy-resolver.test.ts`; the Studio half by `apps/studio/src/lib/policy-form.spec.ts` (raw↔form mapping, clamping) + `apps/studio/src/components/PolicyPanel.spec.tsx` (jsdom: switches toggle, Save PUTs, encrypted warning).
- **Writes are lockable per collection; identity is engine-bound** — a collection may declare, in `schema_json.policies` (set at create or via `PUT /api/collections/:slug/policies`; admin-only), `writes: { mode: 'service' | 'any', append_only, frozen_fields: string[], freeze_when: { field, values[] } }` and `actor_fields: string[]`. Enforced in `ItemMutationService.assertGenericWrite` / `stripFrozenFields` / `assertNotFrozen` / `bindActorFields` on the already-cached schema (zero extra D1 reads) and **inside** the service, so the RBAC admin bypass cannot reach a service-only table. `mode: 'service'` ⇒ the generic entity API is 403 (only the domain service writes); `append_only` ⇒ update/delete/restore rejected; `frozen_fields` ⇒ workflow columns silently stripped from a generic write (only the service sets them); `freeze_when` ⇒ once `row[field]` is one of `values` the row is POSTED and update/delete/restore are 403 (a state-conditional freeze — what makes a posted document immutable); `actor_fields` ⇒ stamped from the signed session on create and un-reassignable by a non-admin (the JWT carries `employee_id` — see `docs/backend-api/authentication.md`). This is what makes a service-owned ledger single-writer and a two-person rule un-forgeable. Pinned by `packages/core/src/policy/__tests__/policy-resolver.test.ts`; see `docs/backend-api/policies-operations.md`.
- **A composite (`table`-field) write drops the CHILD collection's cached reads too** — `ChildTableService.createChildren` / `replaceChildren` land rows in the child collection's OWN table, so invalidating only the parent slug left a reader keyed on the child collection (the document page's own line read, `filter[parent_id][_eq]=…`) serving the PRE-SAVE lines until the response cache's TTL — a draft could be saved (its children replaced delete-and-recreate) and reopening it showed the old lines. Both writers now end by calling `invalidateCollectionReads(childSlug)`, which clears `readc:<child>:*` plus its `readdep:` tag AND, through the recorded observer, names the child in the write's `meta.changed.collections`, so clients drop it precisely too. Pinned by `apps/api/test/child-table-cache.spec.ts` (a raw-D1 mutation proves the cache entry is genuinely live, then a composite PUT _and_ CREATE must be reflected on the very next child read, and the envelope must name the child).
- **The response cache is dependency-tagged, not own-rows-gated** — a `?fields=`-expanded read IS cached: `ItemQueryService.readDependencies()` walks the selection and returns the set of collection slugs the payload embeds (recursively, depth ≤ 3; `null` ⇒ unbounded ⇒ never cached), stored on the entry as tags. A write to any embedded collection drops the entry even though the writer only knows its own slug (`invalidateCollectionReads` also calls `cache.invalidateTag('readdep:<slug>')`). This replaced a coarse "relation reads are never cached" gate. Pinned by `apps/api/test/relation-cache.spec.ts` + `packages/core/src/cache/__tests__/{cache-layer,response-cache}.test.ts`.
- **The hook depth guard is scoped to the async chain, not the isolate** — `withDepthGuard` (`core/plugin-hooks.ts`) keeps its depth in an `AsyncLocalStorage`, because `after_*` hooks are dispatched FIRE-AND-FORGET: a shared module-level counter let a hook backlog from one request inflate the depth a LATER unrelated request observed, 500-ing a write that had no recursion at all ("Hook recursion cap reached"). A genuinely recursive chain still trips `MAX_HOOK_DEPTH`; two independent chains no longer share a budget.
- **Search mode is a per-collection policy (`contains` vs index-backed `prefix`)** — the generic `?search=` term matches via `schema_json.policies.search: { mode: 'contains' | 'prefix', fields: string[] }`, resolved by the same PolicyResolver that carries `cache`/`writes`. `contains` (`LIKE '%term%'`, the default, any collection) is correct everywhere but a leading wildcard cannot use an index; `prefix` (`LIKE 'term%'`) is the type-ahead shape ERP list screens use and an ordinary index on a declared `fields` entry serves it as a bounded range seek. Prefix applies only when ≥1 declared field is a real column, else the read falls back to contains (deny-by-default: an undeclared collection keeps today's behavior). The term is **escaped in both modes** (`LIKE ? ESCAPE '\'`), so a literal `%`/`_` matches its own bytes instead of every row — that was a silently-wrong result, not noise. Emitted in one place (`QueryParser.applyToQueryBuilder`, threaded from `ItemQueryService.listItems`/`runAggregate`); a collection declares `prefix` over an indexed column for a client type-ahead. Pinned by `packages/core/src/policy/__tests__/policy-resolver.test.ts`; see `docs/backend-api/policies-operations.md`.
- **Integrity is a per-collection policy (`policies.integrity`) — a generic anomaly engine** — a collection declares bounded data-quality rules (`orphan` | `aggregate_mismatch` | `duplicate` | `stale`) and `GET /api/collections/:slug/integrity` runs them (read-gated; `{enabled:false}` when undeclared). Every identifier is validated against the live schema BEFORE any SQL (no unknown table/column, no injection) and every rule is LIMIT-bounded (probes one past → `truncated`); a malformed rule is isolated in `errors[]`, never fatal. OFF until declared. `IntegrityService` (`apps/api/src/lib/services/integrity.service.ts`) + `routes/integrity.ts`; pinned by `apps/api/test/integrity.spec.ts` + the resolver test.
- **Permission lineage — every `_role_permissions` row says WHO wrote it** — `source` (`admin` | `provisioner` | `manifest`) + `source_module` (the owning module id when a `ModuleManifest` declares the grant), added by migration `036_role_permissions_lineage` and returned by `GET /api/users/permissions/:role_id`. `AuthService.setPermission` defaults `source:'admin'`; the Telegram role provisioner writes `provisioner`. Existing rows stay `null`. Pinned by `apps/api/test/role-lineage.spec.ts`.
- **Add-ons install/remove at runtime — a module is live only when available ∩ installed** — the build allowlist is `DOMAIN_MODULES`/`PLUGINS`; the runtime state is the `_addons` table (migration `037_addons`). The route gate in `domain-modules/index.ts` ANDs both, and `bootModuleHooks` registers an add-on's compiled hooks only when installed (once per isolate). `ModuleManifest` carries `scope` / `depends` / `provides` / `requires` / `extends`; `resolveAddons` (`@mmbix/types`) resolves the graph + issues. `GET /api/addons` (catalog + state), `POST /api/addons/:id/install|uninstall` (admin, validates deps/extends/capabilities; uninstall refused while depended on). Installed set memoized per isolate (`lib/addon-registry.ts`), invalidated on write. `GET /api/meta` stays I/O-free (build allowlist only). Pinned by `apps/api/test/addons.spec.ts` + `resolveAddons` unit tests; see `docs/backend-api/addons.md`.
- **Governed generation is a gated plugin — the pipeline PROPOSES, the human gate WRITES** — `DesignDNA` (markup-free by construction, bounded) → `inferFields()` (rules-first, pinned table in `packages/core/src/inference/field-inference.ts`; a declared sample format outranks a rule; a non-`VALID_FIELD_TYPES` result is dropped + warned, never invented) → `SchemaProposal` with per-field **visible inference** → states `draft → review → promoted → live` (`rejected` terminal) over `_generation_proposals`, every transition a compare-and-set; `apply` is the ONLY schema write and is idempotent on replay. Shipped as the **`generation` plugin** (`apps/api/src/plugins/generation/`, `/api/generation`, disabled by `PLUGINS`) with an admin gate — the intentional deviation from the draft's "factory core" scope, so it compiles out. The **DSL** is ONE module, `@mmbix/types/dsl`: generic columnar `encodeColumns`/`decodeColumns` + the relocated `meta-codec` (Studio keeps a re-export shim) + pure `applyOps` (`ADD/MOVE/REMOVE/UPDATE/BIND/SPLIT`, idempotent by id, `O(ops)`). A bare **prompt** is normalized deterministically to DNA (`prompt-dna.ts`, no LLM call; an LLM fallback stays behind `generation.allow_llm_fallback`, unused in v1). A declared **relation** that implies a FK becomes a reviewable `m2o` field (`proposal.ts`) materialized on apply ONLY when the target collection exists (`service.ts`). ### Conventions

- **Collections can be created via the Studio schema designer OR `POST /api/entities` OR `headless collection create`** — all paths converge on the same service. There IS a UI schema builder (the earlier "no UI schema builder" rule is obsolete).
- **A field is required (NOT NULL) unless `required: false` is explicit** — callers that build field lists must send `required: false` for optional fields.
- **`unique` is soft-delete-aware** — enforced by ONE partial index (`uidx_<table>_<col>` … `WHERE deleted_at IS NULL`), the same rule the engine's uniqueness pre-check and every read use, so a soft-deleted record never squats its value. Emitted identically by `SchemaBuilder.createTable`, `EntityMigrator` (in-place + rebuild) and the schema sweep; the sweep also normalizes a legacy inline `UNIQUE` constraint (an undeletable auto-index) into that shape. A raw DB unique violation maps to **400** `VALIDATION_ERROR` via `constraintViolation` (`packages/core/src/db/repository.ts` — the single classifier the Repository and the error handler share), never a 502. Pinned by `apps/api/test/unique-soft-delete.spec.ts`.
- **Business modules are opt-in verticals, declared by a `ModuleManifest`** — a vertical lives in `apps/api/src/domain-modules/<id>/` (its `routes.ts` + `manifest.ts`) and is pushed into `moduleManifests` in `domain-modules/index.ts`; `DOMAIN_MODULES` (`infra/env.prod`) gates it — a disabled module is a 404 and registers NOTHING (no routes, no hooks; `bootModuleHooks` runs an enabled module's compiled hooks once per isolate). This repo ships ONE factory-level module: `idp`. The factory core (`routes/`, `plugins/`, `lib/`, `services/`) never imports a module. Built-in plugins are gated the same way by `PLUGINS` (unset ⇒ all; `none` ⇒ none; a list ⇒ only those; disabled plugin routes 404 and their migrations are skipped). New verticals = copy a `domain-modules/<id>` folder or scaffold via the CLI. Pinned by `apps/api/test/gating.spec.ts`.
- **The IDP domain-module (`/api/idp`) is the Studio's operate + govern surface** — catalog/scorecard/usage/templates reads + admin-gated environments/deployments/ownership writes and a `draft → review → promoted → live` deployment workflow. Three invariants keep it sound: (1) its four `idp_*` collections are provisioned once per isolate by an `app.use('*')` middleware (`IdpService.ensureCollections`, promise-memoized) — never lazily on one route only, or the first writer hits a missing table; (2) every workflow transition mirrors `to_state` onto `idp_deployment.status` (catalog + scorecard read that column, so it must never drift from `_workflow_states`); (3) raw writes/DDL in `IdpService` must call `invalidateCollectionReads()` / `SchemaService.invalidateCache()` — the engine's own writes do, and skipping it serves stale rows. Promotion + generic transitions are `requireAdmin`; pinned by `apps/api/test/idp.spec.ts`.
- **Design-system changes require a DS build** — `pnpm --filter @mmbix/design-system build` (components, widgets, exports).
- **Error codes are a canonical contract, not literals** — the single source is `@mmbix/types/contract.ts` (`ERROR_CODES`, `STATUS_TO_ERROR_CODE`, `errorCodeForStatus`). Any new failure code MUST be added to the catalog, not hardcoded: `fail()`, the error handler, and `@mmbix/sdk` typed errors all read from it, `GET /api/meta` advertises `data.error_codes`, and `apps/api/test/contract.spec.ts` pins it. Never hand-write a second error-code map (that was the drift this removed).
- The schema cache (`packages/core` CacheLayer) must be invalidated after DDL changes (create/update/delete collection, seed reset clears it via `cache.clear()`).
- **Studio URL/history contract — one rule everywhere** (`apps/studio/src/lib/view-state.ts`): a route PATH is real navigation (`navigate()`/`<Link>`, push); a route's QUERY PARAMS are that screen's view state and must never create history entries. All Studio URL-backed state MUST go through the `useViewState()` hook (`update`/`commit` rewrite the current entry — replace, never push) so each screen owns exactly one history entry and the back arrow leaves it in one press. Explicit "← Back" buttons must call `popBack(navigate, fallback)` (pop the entry beneath when one exists). NEVER call `useSearchParams().setSearchParams` directly.
